## Case study content structure

HRMS and Stock Analytics follow this flow, in order:

1. **Problem Statement** — the business problem in plain terms.
2. **As-is analysis** — how the process/system worked before, and what was wrong with it.
3. **To-be solution** — what was proposed/built to fix it.
4. **User Stories & Acceptance Criteria** — the requirements that came out of the analysis.
5. **Supporting artifacts** — diagrams, ERD, API specs, etc., as evidence, not as the headline.

Momen drops step 2: it's a greenfield product the team built themselves, not a system being replaced, so there's no As-Is to analyze — it goes straight from Problem to To-Be. Its User Stories are also written by re-framing the team's real feature set as "As a user, I want..." rather than sourced from a formal backlog or interviews — call this out as derived, not as literal project artifacts.

The point is to show BA problem-solving thinking, not just list documents produced. Layout should make this flow visually scannable so a recruiter gets the analytical thread in a few seconds, not just a wall of deliverables.

Only claim outcome metrics (%, $, time saved) that are real/measurable — course-project numbers that were never actually measured should be left out rather than presented as results (see HRMS case: no outcome metrics section, since those numbers were assumed for the class assignment, not measured).

This also covers simulated budget figures, not just outcomes: all three projects (HRMS, Stock Analytics, Momen) are course assignments, so specific dollar amounts (e.g. "$11,000 budget") shouldn't appear even when just describing scope or constraints — describe the constraint qualitatively (e.g. "within the team's timeline") instead.

Same for simulated/AI-generated user research: if a source report contains a "user interview" that was actually AI-generated (as in the Stock Analytics report), never quote or attribute it as real primary research. Drop it, or reframe as the team's own analysis/reasoning without a fake "user said X".

Don't assert anything that can't actually be verified, even when it sounds like harmless framing. Example: Momen's As-Is section originally said "isn't a redesign of an existing platform" and "no system to replace" — there's no way to know that no comparable product existed before Momen, so that got rewritten as a description of common habits ("many people...", "typically...") instead of a claim about the competitive landscape. When in doubt, describe what the team actually did or observed, not what is or isn't true beyond that.
